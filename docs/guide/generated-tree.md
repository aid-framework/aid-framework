# The generated tree

`aid gen` writes into `app/`. This page is what lands there, which files are yours, and what
happens on the second run.

## Two numbers, one rule

| Tree | Files it ships | Managed by the generator |
| --- | --- | --- |
| The tutorial from [getting started](getting-started.md) | 24 | 21 |
| `examples/support-copilot` | 62 | 44 |

The difference is not the generator being inconsistent. It is the rule: **the generator only
manages what it can reproduce from the spec.** A file you write - `app/main.py`, an eval
dataset, a baseline, a document a retriever reads - appears on disk and never in the manifest.
`app/app.spec.yaml` and `app/aid.manifest.json` are always unmanaged, for the obvious reason.

The tutorial tree, in full:

```text
app/
  aid.manifest.json                     unmanaged
  app.spec.yaml                         unmanaged
  business/
    __init__.py                         business
    prompts/__init__.py                 business
    tools/__init__.py                   business
  generated/
    __init__.py                         generated
    contracts/__init__.py               generated
    deps.py                             generated
    evals/__init__.py                   generated
    gateway/__init__.py                 generated
    gateway/models.py                   generated
    guardrails.py                       generated
    observability.py                    generated
    pipelines/__init__.py               generated
    pipelines/hello.py                  generated
    prompts/__init__.py                 generated
    prompts/greet.py                    generated
    requests.py                         generated
    routes/__init__.py                  generated
    routes/hello.py                     generated
    schemas.py                          generated
    tools/__init__.py                   generated
.github/
  workflows/
    ci.yml                              scaffold
    evals.yml                           scaffold, when a `gate.ci` eval is declared
    infra-plan.yml                      scaffold
```

`evals.yml` is scaffolded when the spec declares an eval with `gate.ci: true`;
`examples/support-copilot` has two, the tutorial has none. `infra-plan.yml` is scaffolded
for every project, because it detects its own inputs instead of assuming an `infra/`
directory exists.

## The three owned tiers

- **`app/generated/**`** is the generator's. It is rewritten whenever the spec or the generator
  changes, so an edit here survives until the next run and then becomes drift.
- **`app/business/**`** is yours. It is created once, never overwritten, never deleted - not
  even by `--force`. Tool bodies, prompt overrides and domain rules live here.
- **`.github/workflows/**`** is scaffolded once and then yours. It is the only thing outside
  `app/`, and it exists because a generated project is not deployable without a pipeline: the
  workflow runs the determinism gate (`aid gen --check`), lint, build and tests on every pull
  request, and checks the committed `infra/` tree against the spec when the project has one.
  The eval workflow runs on demand and nightly, because it measures a real model and a pull request
  from a fork cannot hold the credential it needs. That same workflow records the spans each eval
  run produces (`.aid-traces`) and reads them back with `aid cost`, so a run reports what it spent;
  setting the repository variable `AID_COST_BUDGET` turns that report into a ceiling the run fails
  against. The infra plan is manual for the same reason the eval run is: it assumes a cloud role
  through OIDC (`AID_INFRA_ROLE_ARN`, `AID_INFRA_REGION`), and a plan against a real account is
  something a human dispatches. It initialises the environment root before calling
  `aid infra plan`, which drives `tofu` or `cdk` but does not run `init` itself.

Every file carries the tier in its first line, so a reader can tell without consulting the
manifest:

```text
# Code generated by AID Framework "@aid-framework/generator-py-fastapi" v0.1.0. DO NOT EDIT.
# Owned by the generator: regenerate with `aid gen`. See aid.manifest.json.
```

```text
# Created once by AID Framework "@aid-framework/generator-py-fastapi" v0.1.0. Edit freely.
# The generator never overwrites this file: it is yours. See aid.manifest.json.
```

```text
# Generated once by `aid gen` for the `py-fastapi` target, then yours.
# A scaffold file is never overwritten and never recorded in aid.manifest.json,
# so edit it freely: a new runner, a cache, an extra toolchain.
```

## What each generated module is for

| Module | Comes from |
| --- | --- |
| `schemas.py` | `types` with `kind: struct` - the response and structured-output models. |
| `requests.py` | One request model per HTTP trigger, derived from the pipeline's declared inputs. |
| `contracts/` | A module per tool, holding its `input` and `output` types. |
| `prompts/<name>.py` | A rendered template per `prompts` entry, plus its variable contract. |
| `pipelines/<name>.py` | The steps as awaitables, in declared order, with guardrail enforcement inlined. |
| `routes/<name>.py` | The HTTP endpoint for one pipeline. |
| `agents.py` | `agent_router`, carrying `POST /agents/{agent_id}/run` and `POST /agents/resume`. |
| `guardrails.py` | The policy table and `guardrail_block`, which turns a block into an HTTP 400. |
| `gateway/models.py` | Model aliases, params, cost profiles and the fallback chain as data. |
| `deps.py` | The `Deps` dataclass, `build_deps()` and the `get_deps()` singleton. |
| `observability.py` | Trace hooks the runtime calls around each step. |
| `sse.py` | Event-stream framing. Emitted for a streaming deployment only. |
| `Dockerfile` | The image a deployment with `target: container` runs. |
| `retrieval/` | `bindings.py` for query-time search, `ingest/<store>.py` for the write path. |
| `evals/<name>.py` | One module per eval, runnable through `aid eval`. |

`retrieval/` is conditional: the tutorial spec declares no retriever and gets neither
`bindings.py` nor `ingest/`, while `support-copilot` gets both. `contracts/__init__.py` is
always emitted because it holds `ToolContext` - the dataclass the generated adapter hands a
tool - even when no tool is declared. `evals/__init__.py` is only a package marker; the eval
modules beside it appear once `evals` is declared.

`Dockerfile` is conditional too, and on a different axis: it exists only when a deployment
declares `target: container`. Where the app runs is the only thing that can justify an image,
and a project that deploys nowhere as a container is not missing a file. Because the build
needs `pyproject.toml`, which sits above `app/`, the context is the application root and the
file is named explicitly:

```console
docker build -f app/generated/Dockerfile -t support-copilot .
docker run --rm -p 8080:8080 -e OPENAI_API_KEY=... support-copilot
```

The image runs `app.main:app` - the same entry point the developer runs locally - as a
non-root user, with `exec` so the platform's `SIGTERM` reaches uvicorn. No secret is a build
argument or an environment layer: the process reads a declared secret when a model is called.

## The manifest

`app/aid.manifest.json` has exactly three top-level keys:

```json
{
  "manifestVersion": 1,
  "generatedBy": {
    "generator": "@aid-framework/generator-py-fastapi",
    "generatorVersion": "0.1.0",
    "irVersion": "0.1.0"
  },
  "files": [
    {
      "path": "app/generated/routes/hello.py",
      "owner": "generated",
      "sha256": "�",
      "generator": "@aid-framework/generator-py-fastapi",
      "generatorVersion": "0.1.0"
    }
  ]
}
```

Two things to read carefully.

**`generatorVersion` is `0.1.0`, not the package version.** The generator plugin declares its own
version in its manifest, independent of the npm package that ships it. This field stays at 0.1.0
across package releases - it is the plugin's contract version, not a stale install. Use `irVersion`
to reason about IR compatibility and `manifestVersion` to reason about the manifest's own shape.

**There is no spec hash.** Drift is computed per file from `sha256` against what is on disk, so
a spec change that does not alter a file leaves it `unchanged`. That is what makes regeneration
cheap and what makes a CI job that runs `aid gen` and asserts a clean tree meaningful.

## The second run

Regenerating an unmodified tree is a no-op, and the summary says so:

```console
$ aid gen
py-fastapi: 0 created, 0 updated, 17 unchanged, 3 kept, 2 scaffold kept
```

`kept` is the important word: it is a `business/` file that already existed, and the generator
declined to touch it. `scaffold kept` is the same promise for a workflow file: it was written
once, it is yours now, and the generator will neither rewrite it nor count an edit as drift.
`unchanged` means a generated file whose bytes already match the plan.

## When you edit a generated file

The manifest hash is the detector. If `app/generated/routes/hello.py` on disk does not match its
recorded hash, the generator treats it as a human edit and:

1. refuses to overwrite it,
2. writes the new bytes beside it as `app/generated/routes/hello.py.aid-rej`,
3. exits non-zero with guidance naming the path.

`--force` discards the edit and rewrites the file. It does **not** touch `business/`. To keep the
edit instead, run `aid eject <path>`: it moves the file to `business/` and stops the generator from
ever planning that path again.

Files that are no longer in the plan are reported as "no longer generated" and left on disk.
Deletion needs an explicit `prune`, because it is the one operation with no recovery.

## What you write

- `app/main.py` - the ASGI entry point. `aid gen` never emits it. See [Serving](serving.md).
- `app/business/tools/__init__.py` - the `IMPLEMENTATIONS` mapping the generated executor reads.
  Adding a tool means adding it here too.
- Any prompt override or tool body the example ships in `business/`.
- `app/evals/*.json` datasets and `*.baseline.json` files.
